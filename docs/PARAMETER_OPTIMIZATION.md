# Parameter optimization under a locked strategy semantics

English | [简体中文](PARAMETER_OPTIMIZATION.zh-CN.md)

Status: Stage 1 and Stage 2 implemented; Stage 3 planned
Last updated: 2026-07-31

## 1. The general capability

The platform discovers tunable numeric slots in any supported machine strategy
contract. Without changing the trading timeframe, the entry and exit actions, the
long/short direction, the indicators and market fields, the comparison
operators, the boolean structure, or the fill timing, it constructs a finite set
of parameter candidates and runs auditable experiments against the same
immutable history.

The capability is not scoped to a particular strategy, instrument, timeframe,
language, or numeric constant. A parameter that cannot be expressed through the
machine contract and the deterministic executor is never marked optimizable just
because a prompt or a single example wants it to be.

## 2. Stage 1: search with locked semantics

### The parameter contract

- Numeric parameters in condition expressions: indicator periods, comparison
  thresholds, and bounded arithmetic constants.
- Decision parameters: position size, stop-loss percentage, and take-profit
  reward-to-risk ratio.
- Indicator lag/offset stays locked by default, so time references and the
  lookahead boundary are never changed unintentionally.
- Every parameter has a stable ID, its original value, a numeric type, a unit, a
  suggested range, and a hard safety bound.
- At most 4 parameters per run, 2–7 values each, and at most 16 candidates per
  round.

The server derives a structural skeleton from the original contract, replacing
the numeric slots that may vary with placeholders, and computes a SHA-256
fingerprint of it. The browser cannot submit a modified contract; it can submit
only parameter IDs and ranges the server issued. Every candidate is generated by
the server from the original contract, re-validated, and compared against the
structural fingerprint again.

Candidates come from a deterministic grid, sampled at fixed positions when the
combination count exceeds the budget. Three deterministic scoring modes are
supported today: robust composite, return-first, and drawdown-first. Low trade
counts, train/validation divergence, and validation drawdown all incur penalties.
If no candidate clears the general improvement bar, the original parameters stay
and no variant is recommended.

## 3. Stage 2: robustness gates

### Time and information isolation

- The first 80% of history is the development range; the final 20% is sealed as
  the one-shot blind set when the experiment is created.
- Roughly the first 70% of the development range is training and the last 30% is
  chronological validation — about 56% / 24% / 20% of total history.
- Indicators may read history before the performance window to warm up, but the
  warm-up range cannot trade, place orders, or contribute to the equity curve.
- Three anchored walk-forward windows then run inside the development range, and
  a candidate must hold its relative return, drawdown, and minimum trade count in
  at least 2 of them.

### Robustness evidence

- Parameter neighborhood: perturb each selected parameter one step up and one
  step down; at least 60% of the valid neighborhood points must not collapse
  significantly.
- Cost pressure: three fee and slippage scenarios — current cost, double cost,
  and severe impact.
- Market regime: report fills, win rate, and net PnL under rising, falling,
  ranging, and high-volatility regimes, classified by relative quantiles of
  rolling return and volatility. This is stratified evidence, not a separate
  pass/fail gate.
- Multiple selection: report the candidate count and a clearly labeled
  selection-penalized Sharpe heuristic. It is not the Deflated Sharpe Ratio and
  does not pose as a test of statistical significance.

The final blind-test button unlocks only when all of these hold at once:
improvement over the original parameters, walk-forward passed, neighborhood
stable, and cost pressure passed.

### The one-shot blind test

- Each experiment's blind-test state is persisted as
  `reserved → running → passed/failed`, with atomic claiming so concurrent
  requests cannot consume it twice.
- The session, strategy version, parameter ranges, data digest, and backtest
  configuration together produce a deterministic experiment ID. An identical
  experiment restores the existing record; you cannot mint a new ID to look at
  the same blind set again.
- Before revealing, the same history range is re-read and the candle digest is
  verified. If the snapshot changed, the run stops rather than mixing in new
  data.
- Candidate parameters are fixed before the reveal. The blind test only accepts
  or rejects; it never participates in re-selecting parameters.
- On first completion an immutable receipt is stored; a repeat request returns
  that same receipt without executing again.
- The minimum bar is at least 2 blind-test trades, with return and drawdown
  relative to the original strategy inside the defined degradation tolerance.

Once the blind test passes, the user can create a new immutable strategy record.
That version keeps its parent strategy, the experiment ID, the semantic lock, the
parameter diff, and its provenance. The web app currently treats the machine
contract as the source of truth for deterministic execution, so a parameter
version is marked `contract-derived` rather than fabricating TypeScript source
that has not been materialized.

## 4. Performance and caching

- One experiment loads candles once; it does not request market data per
  candidate.
- Historical reads go in this order: local static library, in-process hot cache,
  R2 persistent cache, official archive cold start, and REST as the last resort.
- The experiment cache key covers the contract, the semantic lock, parameter
  ranges, the objective, the budget, the backtest configuration, the candle
  digest, and the engine version.
- Full experiment receipts and blind-test state go to D1, repeated computation
  results go to R2, and an in-process hot cache removes duplicate execution
  within one instance.
- A synchronous Worker still suits only small bounded experiments. Larger search
  spaces and concurrent users need an async task queue, concurrency quotas,
  cancellation, retries, and persisted progress.

## 5. Real boundaries today, and what comes next

- The Stage 2 bar is engineered robustness filtering. It is not a guarantee of
  future returns or a formal proof of statistical significance.
- Market regimes use in-sample relative quantiles; no external macro labels or
  cross-market validation yet.
- Cost pressure is bar-level: no order-book impact, queueing, latency
  distribution, or capacity model.
- Materializing program source for a new parameter version is not implemented.
  Web backtests execute its server-side contract, and the source field stays
  empty with its provenance clearly marked.
- Login, object ownership, paid quotas, and long async jobs are still incomplete.

Stage 3 is the "AI experiment researcher". The model may explain parameters,
suggest bounded ranges, propose the next round, and describe fragility. It may
not rewrite indicators, widen safety bounds, keep fitting after reading the final
blind set, or disguise a structural change as parameter optimization. Any change
to an indicator, rule, or action must create an explicit strategy branch and be
confirmed by the user.

## 6. Generalization acceptance evidence

- Original regression: arithmetic drawdown ratios and equity-based position sizes
  still execute through the full backtest.
- Parameter variant: a comparison threshold and a stop-loss percentage can enter
  a bounded experiment together.
- Structural variant: an RSI period and threshold are discoverable while lag=0
  stays locked.
- Boundary rejection: an unknown parameter ID returns 400 before execution; when
  a pre-gate fails, the blind set stays sealed and is never read.
- One-shot state: identical inputs map to one experiment; a second blind-test
  request reuses the receipt; a second version-creation request reuses the same
  strategy ID.
- Semantic consistency: every candidate and every new version re-passes contract
  validation and the structural fingerprint comparison.
- Existing regression: the web build, server-side rendering, and the full
  automated test suite still pass.
